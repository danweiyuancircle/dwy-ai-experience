# 版本与源码定位

## 每个实际使用的包分别核对

1. 查消费项目 `pubspec.yaml` 的依赖来源与约束，同时查 `dependency_overrides`、`pubspec_overrides.yaml`。workspace 还要检查根和成员的覆盖配置。
2. 查生效的 `pubspec.lock`；workspace 使用根目录共享锁文件。声明范围不是实际版本，Git 的分支名/tag 不是最终提交。
3. 查生效的 `.dart_tool/package_config.json` 中该包的 `rootUri`，相对 URI 按配置文件位置解析。workspace 使用共享配置；从实际指向的目录读取源码，不根据目录名猜版本。
4. 在实际源码核对包名、pubspec、公开导出、目标 API、README、测试与示例；相关平台插件和 UI 类型也按本次解析版本确认。文档未随包分发时，再查同一发布版本/提交的仓库资料。

只记录本次涉及包的名称、来源、实际版本/提交或路径，以及支持所用 API 的证据；不输出凭据或带凭据的源地址。

| 生效来源 | 如何确定依据 |
| --- | --- |
| hosted | 锁文件中的 registry、精确版本及实际缓存源码；不能直接套用 pub.dev 最新文档 |
| Git | 锁文件中的 `resolved-ref`、仓库及包子目录；查该提交源码，不跟随当前分支头 |
| path | 配置指向的实际目录及其源码；有 Git 时核对提交与相关未提交差异，没有 Git 时也不能把 pubspec 版本当作不可变快照 |
| workspace 成员 | 共享配置指向的成员源码、当前提交及相关未提交差异；成员包不一定作为外部依赖出现在锁文件中 |

覆盖依赖生效时按覆盖后的来源核对。相同包名与 `version` 可对应不同提交、路径或本地修改，多个包也可能分别来自不同来源，不能统一按一个版本号接入。

## 缺少解析结果或证据冲突

- 尚无有效解析产物时，按项目 Flutter/Dart 工具链执行对应 `pub get` 后核对，并检查锁文件变化。不要用 `pub upgrade`、删锁文件或临时 overrides 来获取想用的 API。
- 声明、锁文件与配置不一致时，先报告冲突；配置只能表明现有工具解析指向，不能证明与当前声明同步。按当前声明重新解析后确认；无法解析时明确未确认项，不宣称兼容或擅自选择最新代码。
- Skill 中有某能力、项目版本却没有时，使用现有 API 能完成需求就沿用；确需升级时列出目标版本/提交、公开接口与配置迁移、受影响调用方及必要验证，按任务授权执行。证据不足时不编造版本矩阵或兼容包装。
- 项目 SDK、包声明下限和实测平台分别核对。本仓当前开发基线不自动适用于旧消费项目；单测通过也不证明原生权限、商店或设备行为通过。

规则依据：[依赖来源与覆盖](https://dart.dev/tools/pub/dependencies)、[workspace 共享解析](https://dart.dev/tools/pub/workspaces)。
