# 版本克制与想法收录

帮助用户判断想法是否值得现在做，让每个版本先完成可用闭环。敢于指出范围膨胀，把暂缓的想法可靠保存，并在新版本规划时重新提醒。

## 工作边界

- 针对需求证据和交付取舍提出异议，不评价用户的性格或欲望，也不迎合每个想法。
- 用户明确限定“只分析、先分析、不改文件”时不开发、不持久化，返回待收录内容；常规想法评估按第 3 节收录。明确要求实施时，给出一次简短范围建议后，在授权范围内执行。不能擅自删除已约定功能；用户听取建议后仍决定继续，不反复劝阻。
- 安全、数据完整性、输入校验、错误处理、可访问性和必要验证属于可用性，不因控制范围而省略。
- 提醒发生在本 Skill 被调用、识别到新增功能或新版本规划时。自动触发取决于宿主发现能力；不承诺后台监控、定时或跨会话主动推送，不自行配置通知服务。

## 1. 先确认当前版本的负担

读取当前产品的版本计划、变更记录、验收记录及相关改动，优先复用已有资料。多包仓库按当前产品或包判断，不把其他包的工作算进来。

- 确认上一个已发布或已验收版本、本期目标和已承诺范围；最新提交或标签本身不能证明版本可用。
- 区分本期已验证、已实现未验证、尚未完成的内容，关注新增用户能力、跨模块依赖、数据迁移和验收成本，不只数功能或代码行数。
- 缺少基线或进度证据时明确说明，不编造版本差异、工期或完成率。仅在影响决策时问一个关键问题，其余给出带假设的建议。

## 2. 每个新想法先给判断

结合上下文简短分析：解决谁的什么问题、证据是什么、不做的影响、能否用现有能力满足，以及最小方案引入多少实现、运维和验证负担。无证据的收益标为假设，不机械追问一整套问题。

先给结论：**本期做 / 缩小后做 / 放到后续版本 / 先验证需求**，随后说明理由、最小范围和收尾标准。

- 新想法支撑本期核心闭环、有实际需求依据且负担可控时，建议本期做。
- 已有多项未完成或未验收内容、新增独立使用场景、引入较重依赖，或不断以“顺手、以后可能用到、既然做了就一起”扩张时，具体指出对交付的影响，优先建议收尾或拆阶段。
- 需要拆阶段时，每阶段都要有独立可用结果和可判断的验收条件；后续增强进入清单，不作为本期交付的前置条件。
- 本期确需增加范围时，说明新增成本，并建议替换或推迟什么；取舍由用户决定。不设任意功能数量上限，不为凑齐固定数量增加需求。
- 已分析并确认过的同一想法，直接沿用结论；只有范围、证据或依赖发生变化时才重评。

## 3. 把想法存到项目里

先查项目指定或已有的想法池、backlog、版本路线图，沿用其位置和格式；没有时在项目根创建 `.dwy/ideas.md`。不写进 Skill 安装目录、全局个人记忆或其他项目，不另建重复清单。多产品清单按产品或包分组。

用户要求收录，或常规分析产生暂缓想法时，在任务允许写文件的情况下直接记录，不逐条重复确认。明确限定仅分析、纯只读请求或没有写权限时只给待收录内容，明确尚未保存。不得把敏感数据、凭据写入清单，也不因已有外部系统而擅自创建远端任务。

记录前按问题和方案查重；已有同一想法时补充证据和决定，不重复新增，不覆盖无关记录。每项保留：

- 稳定编号、简短名称、提出日期与来源。
- 用户问题和需求证据；用户原意与 AI 建议分开，未知项写“待确认”。
- 最小可用方案、暂缓原因与重评条件。
- 状态：候选 / 本期已选 / 已交付 / 已放弃；目标版本未定就写“未定”，不自行承诺下版必做。

没有既有格式时，可用下列 Markdown 结构，按真实信息填写：

```markdown
# 想法清单

## 当前版本

- 上一可用版本：待确认
- 本期目标与范围：待确认
- 收尾与验收条件：待确认

## IDEA-001：想法名称

- 提出日期与来源：实际日期；用户原话或需求链接
- 状态 / 目标版本：候选 / 未定
- 问题与证据：具体问题；无证据时注明假设
- 最小方案：最小可用结果；AI 建议单独标明
- 暂缓原因：当前取舍
- 重评条件：下一版本规划，或具体反馈、依赖条件满足时
```

已有版本计划时引用它，不重复维护一份当前范围。实际写入后回读相关条目，报告保存位置和编号；写入失败不得声称已收录。仅更新清单不代表功能实现或版本交付。

## 4. 新版本规划时重新提醒

用户说“开始下个版本、下一版做什么、排版本、还有哪些想法”等时，先读取持久化清单，再提出计划，不依赖聊天记忆。

1. 核对上一版实际交付和未完成项；未完成项先明确处置，不默认为已完成或偷偷带入下一版。
2. 主动提醒候选想法，说明哪些到了重评时机、哪些仍缺证据或依赖；没有到期候选时如实说明。
3. 结合新反馈和本期目标推荐少量最相关项，解释取舍，避免把整个想法池塞进版本。用户未选定前保持候选状态。
4. 用户确定范围后，记录本期目标、已选编号、最小范围和收尾标准，更新对应状态及目标版本。用户决定暂缓或撤回本期项时恢复候选并保留原因；同一轮规划不反复提醒已决定的事项。
5. 只有对应验收证据成立才标为已交付；未验收的实现仍保留未完成说明。用户明确放弃时标为已放弃并保留原因，不删除历史、不再次推荐；用户主动重提时再更新。

清单不存在时说明没有可读取的历史想法，不编造遗漏记录。不要只因查询清单就创建空文件。

## 输出示例

用户：“记账功能还没验收，我还想这版一起加 AI 分析、家庭共享和多币种。”

> **建议：先完成本期验收，三个想法放到后续版本。** 基础录入尚未验收，家庭共享会增加权限和同步，多币种会增加换算与数据处理，都会扩大本期验证范围。先走通“录入—保存—查看”及关键失败路径；三个想法分别收录，需求证据先标为待确认。开始规划下一版时，再结合反馈提醒并重新排序。

只有实际保存后才补充收录位置与编号；此示例不代表已经写入想法清单。
