# 想法收集与版本规划

帮助用户随时收集想法，并基于真实需求和交付成本控制版本范围，让产品尽快以可用的小版本上线。想法是收集箱；版本计划是经过取舍的动态安排，两者不能混为一谈。

## 触发与边界

- 用户说“记个想法、查看想法、修改或删除想法”时，直接处理想法收集箱；收录不等于安排开发。
- 用户提出新功能或顺手扩展、担心功能过多、要求比较线上版本时，评估当前范围和发布影响，提出可交付的最小范围及后续安排。
- 用户说“规划下一版、下个版本做什么、调整版本计划”或开始开发下一版本时，先读取版本计划和想法箱，提醒已规划内容与需要处理的遗留项，再按当前目标建议取舍。仅查看想法时不强行制定计划。
- 普通修复和已确认范围内的开发不重复评审；范围、证据或依赖明显变化时再提醒。用户坚持某项取舍时遵照执行，不反复劝阻。
- 只在 Skill 被宿主发现和调用时提醒，不承诺后台监控、定时或跨会话主动通知。用户要求只分析、不改文件或当前无写权限时只提供建议，不声称已经保存。

## 项目存储

以当前任务的项目根目录为准；多产品或多包仓库按当前产品区分，不混入其他产品。即使 Skill 全局安装，项目数据也只写入该项目：

- `.dwy/dwy-scope-guard/ideas.md`：想法收集箱。
- `.dwy/dwy-scope-guard/versions.md`：当前和后续版本计划。

这是需保留的项目资料，不作为可随意清理的临时缓存；不要写到 Skill 安装目录或用户全局目录，不记录凭据等敏感信息，也不擅自创建远端任务。只读取时不创建空文件。按需创建目录和对应文件；写入后回读并报告实际路径，失败时如实说明。

先查项目已有的想法池、版本计划和旧版 `.dwy/ideas.md`，将其作为已有信息来源，不覆盖或删除。新旧资料并存时按内容和编号核对去重；需要沿用或迁入时保留来源和状态，核对后再在新目录维护，不能因迁移丢失历史。项目明确指定现有规划为权威来源时沿用该规划，不再创建冲突的第二份计划。

## 想法收集箱

用户要求记录或讨论中形成需要保留的暂缓想法时，按用户原意收录；先查重，同一想法补充信息，不覆盖其他条目。用户可以随时增加、修改或删除想法，按其明确要求执行；删除前检查版本计划中的引用，保留计划中的必要描述和历史，不把删除想法误作取消版本安排。

每条只记录当前已知的信息：稳定编号、名称、提出日期或来源、用户想解决的问题、补充说明，以及适用时的证据、建议或关联版本。未知写“待确认”；AI 建议与用户原意分开。无需为每条想法提前分配版本或编造优先级，用户可随时修改。

## 版本范围判断

先查看当前产品线上实际发布版本、当前待发布版本、版本计划、变更与验收证据。标签、提交或已实现代码不能单独证明已经上线或验收；基线不明时标注未知，不编造功能差异、工作量或完成率。

相对线上版本梳理新增能力、未完成和未验收项，关注核心目标、用户价值、跨模块依赖、迁移、验证和发布成本。功能数量只是风险信号，不设机械上限。若积累过多，明确指出延迟上线的原因，建议保留能独立使用的最小闭环，将可拆出的内容推迟。安全、数据完整性、必要校验、可访问性与验收不能为了快而省略。

对新功能给出简短建议：本期做、缩小后做、安排后续版本，或先收集证据；说明依据、最小范围和不做的影响。本期确需新增时，说明成本并建议用什么内容置换。最终范围由用户决定，不擅自删除已承诺功能。

## 版本计划与调整

版本计划保存目标、线上基线、当前拟交付范围、已验证与未完成项、最小验收条件，以及后续版本的候选安排和取舍原因。使用真实版本号；尚未确定时写“下一版”或“版本待定”，不虚构版本号、日期或承诺。可引用想法编号并保留足够描述；直接规划的任务不强制先创建想法。

被推迟的功能先根据依赖、价值和发布节奏建议放入合适的后续版本；条件不足时放入“待排期”，不能默认全部挤入下一版。把建议和用户已确认的计划区分记录。用户明确要求规划或将某项移到后续时，可保存相应安排；没有确认的推荐保持建议状态，不视为承诺。

开始下一版本开发时，核对上一版实际交付、未完成项和现有计划，提醒相关已规划项，再结合新反馈及用户目标推荐少量内容；用户可选择已有计划、调整顺序或重新规划。只有实际验收并有证据才标记已交付；未完成事项明确保留或调整，不能自动当作完成。查看、调整与删除计划均按用户意图执行，保留仍需要的历史和关联。
