# 审查与复用判断

## 审查范围

从最终变更出发，追踪调用方、被调用模块、公共接口、测试、配置、迁移和文档。项目有代码索引时按项目规则使用并核实当前源码；没有索引就使用现有搜索能力，不自动建立索引。

先复用项目的格式、类型、依赖边界等现有检查，AI 再审查工具无法覆盖的语义；不为一次审查搭建新平台。改动小也要检查相关边界；不扩大成全仓重构。单独审查不以测试全绿为前提，测试缺口限制相应结论，不阻止其他有证据的分析。

| 维度 | 必须回答的问题 |
| --- | --- |
| 需求与正确性 | 是否满足需求？边界输入、错误、权限、并发和兼容性是否按实际风险验证？ |
| 代码规范 | 是否符合项目规则？是否复用了现有能力？是否增加无依据的兜底、重复实现或多余抽象？ |
| 架构 | 依赖方向是否符合现有架构？是否有循环依赖、基础层依赖业务、实现细节泄漏？没有明确分层约定时，根据实际职责和调用关系判断，不强推某种架构。 |
| 模块边界 | 职责与生命周期是否清晰？业务规则与基础设施能否分别变化和测试？抽取后调用方是否更简单？ |
| 验证与交付 | 测试是否证明行为且对应当前代码？调用方、导出、迁移、文档是否同步？哪些运行环境尚未验证？ |
| 复用机会 | 是已有能力未复用、可沉淀的新能力，还是仅代码相似？有什么真实消费者或稳定契约证据？ |

每条问题提供文件位置、触发条件或调用关系、实际影响、最小修复建议及验证方式。区分已确认问题与待验证疑点；没读过的代码不作确定结论。

## 问题等级

- **阻断**：需求不满足、可证明的行为缺陷、安全或数据损失风险、公共接口不兼容、违反项目明确的架构约束。确认的问题解决前不能判定通过。
- **建议**：尚无实际影响的可读性、整理或抽取机会。不能把个人风格偏好当作阻断理由。
- **待验证**：证据不足。影响必需验收条件时结论为未完成，否则说明疑点与剩余验证，不伪装成已确认缺陷。

## 抽取决策

先根据当前项目的依赖、源码和文档识别团队自己的基础库，不硬编码库名；社区依赖不算团队基础库。没有依据时明确写「未识别」，不假设存在目标库。

| 类型 | 合适落点 | 核对条件 |
| --- | --- | --- |
| 业务无关 | 已有通用基础库的对应模块 | 接口不依赖业务实体、项目单例、宿主导航或私有配置；必要的安全校验与错误语义保留。 |
| 业务相关但跨项目稳定 | 领域模块或领域库 | 明确共同业务契约与差异；宿主策略通过已有合理边界注入，不把不同规则强塞进通用接口。 |
| 当前项目特有 | 项目内部业务模块 | 按职责归位；没有复用证据时保留，避免提前做公共库。 |

真实的第二个消费者、已有稳定公共契约、或已确认的跨项目需求可支持抽取；仅名称相近或「以后可能用到」不足。比较迁移、版本兼容、测试与维护成本，成本大于收益时记录暂不抽取的原因。

初步候选只记录来源、分类、复用证据、未直接抽取原因和下一步；需要实施时再补齐已有能力检索结果、消费者、目标接口及迁移兼容成本。落地后将状态改为已落地，在项目既有能力目录记录实际入口、版本、调用方和验证结果；没有目录时更新同一候选记录，不新建管理平台。开发前检索这些记录并核实实际代码。

记录不包含凭据、个人信息或业务敏感原文；公共库还需确认内容适合公开。非本轮必需的抽取与整理不拖延交付，集中列为后续决策。

任务范围内且已获授权的模块整理可以直接执行并验证。跨仓库抽取、破坏性 API 变更、新运行时依赖和发布按已有授权及项目规则处理；记录候选不等于授权实施，已授权的动作不重复询问。

## 审查记录契约

小范围、低风险改动在最终回复或项目既有任务记录中简要说明改动、验证、审查与复用结论，不强制新建报告或计算内容哈希。涉及公共接口、架构、迁移、安全、部署或复杂跨模块改动时保存完整报告；项目明确要求完整报告时遵守项目约定。

完整报告使用以下结构，不需要额外创建空清单或强制 JSON：

1. **结论**：通过 / 需修复 / 未完成，并注明是开发交付还是只读审查。只读审查可以完成并给出结论，不代表功能开发、测试或部署验收通过。
2. **范围与快照**：需求、任务路径、基准提交及任务变更的内容摘要（含新增、删除、未跟踪内容）；无 Git 时使用文件内容摘要。记录独立审查或自审及未覆盖范围。
3. **验证**：实际执行的检查命令、结果、对应快照和未验证项；必需项无法执行时结论不得为通过。
4. **发现与处理**：按等级记录证据、修复、复测和剩余问题；无发现则明确说明。
5. **复用决策**：逐项记录候选、复用已有能力或无需抽取及理由。
6. **后续动作**：先完成当前授权内可执行的动作，再集中列交付验收确认、可选后续决策或无法自行解除的阻断；不把常规实施选择交还用户。提交、推送、发布及跨仓库操作遵守已有授权，不能用事后确认替代必要的事前授权。

例：账号设置页面既包含通用邮箱输入，也包含当前产品的购买门槛。先查已有输入组件；组件可复用时直接使用。购买门槛留在宿主业务模块。账号管理流程只有在共同契约明确后才成为领域库候选，不能因两个页面相似就把购买逻辑一起移入公共 UI 库。
