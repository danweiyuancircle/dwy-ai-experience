# 项目需求澄清

## 1. 找到原始需求并查清现状

优先用对话和项目资料里的单号、链接或需求标题定位 Jira 和飞书原文。已有线索时，用环境中可用的 `jira-integration`、`lark-doc` 或项目已有的只读入口查阅。阅读正文、验收条件和与当前需求直接相关的关联文档，记录实际读到的出处。检索限定在目标项目及本次需求。

- 找不到原文时，先问用户是否有 Jira 单号、飞书链接或可以贴出的需求原文。找到多个可能对应的文档时，列出候选并请用户指明。链接存在但无法读取时，说明具体情况，请用户提供可访问链接或相关内容。
- 用户已说明没有原始文档，或明确要求按聊天内容继续时，直接以用户输入为依据展开讨论。
- 原文与用户描述有冲突时，指出发生冲突的规则，给出能看出结果差异的场景，请用户确认本期采用的预期。

沿实际入口追踪相关代码、数据和配置，检查现有测试及实际启用的调用方。定位规则的实现位置，核实哪些入口共用以及改动影响。新项目或尚未实现的功能，以可取得的设计资料、接口约定和相邻功能为依据，注明资料缺口。

用几句话说明当前理解、已核实的行为，以及用户希望改变的地方。代码和测试用于确认现有行为及影响范围。目标行为以原始需求和用户确认的规则为依据。

## 2. 用场景分轮确认

1. 从已知入口、数据和状态中挑出会改变交付范围、用户结果或验收判定的分支。优先问主流程和分支选择规则，再按回答追问受影响的异常、边界、旧数据、权限或既有流程。仅检查与该需求有关的分支。
2. 每轮先简述当前理解，再列出少量前提已明确、用户可以直接决定的场景。给每个待确认场景编号，写清「前置条件 → 具体输入或操作 → 预期结果」，方便用户逐条回复。存在多种合理预期时，给出具体选项和推荐理由，允许用户提出其他做法。能查明的项目事实先自行核实。
3. 收到回答后记录已定规则，更新受影响的场景，再追问新出现的分支。只在新答案与已定规则冲突时重新确认。用户明确交由你决定的事项，写明实际选择及依据。
4. 问题发出后等待回答。用户要求跳过的分支，按用户决定记为本期范围外或待后续确认。只要还存在会改变本期行为、影响范围或验收结果的未决问题，就继续只读核查和提问。用户要求先出文档时，标为草稿并列明未决项。

### 提问示例

假设需求是「重新打开应用时恢复上次使用的直播频道」，并且已核实频道选择发生在播放成功之前。

- 第一轮。用户正在播放 A，切到 B 后 B 播放失败，随后退出。重新打开时恢复 A，还是重试 B？若目标是恢复上次实际观看的频道，建议恢复 A。若目标是恢复用户最后一次选择，建议重试 B。
- 假设用户选 A。下一轮。用户上次成功播放的是 A，但重新打开时 A 已下线。此时直接播放项目默认频道，还是停在频道列表让用户选择？若项目已有首播规则，先核实，再说明沿用该规则时用户会看到什么。

## 3. 确认范围并定稿

定稿前给用户一份确认稿，允许用户逐条修改或一次确认整稿。已有用户确认且适用于当前项目的整稿可直接沿用，只追问新增或冲突的部分。

- **需求理解**。简述当前行为、目标行为、适用入口和范围，以及讨论过的相邻行为如何处理。
- **验收场景与边界**。用列表或表格列出「编号、前置条件、输入或操作、预期结果、确认状态」。每个影响本期行为的边界单独列出。预期写可观察结果，例如「输入已停用的频道号 → 保持当前频道播放并提示频道不可用」。用户已明确确认的结果标为已确认，其余标为待确认。
- **最小改动边界**。沿实际调用链列出必须改动的入口和逻辑。逐项判断省去这项改动会让哪条验收场景无法通过、哪项既有业务行为或兼容约定无法保持，或哪项必要验证无法执行。只有能说明具体影响的改动才纳入本期。重构、抽象、性能优化、顺手修复和清理都按同一标准判断，超出本期需求的事项由用户单独确认后才能纳入。

当每个影响本期实施或验收的场景都已有明确预期，并且用户确认整稿或明确确认全部相关条目后，定稿需求文档。

沿用用户指定的文档位置或项目已有的需求模板。两者都没有时，在 `docs/requirements/` 保存一份 Markdown，包含以下内容。

- 背景与目标。写清当前行为和想解决的问题。
- 本期范围。说明涉及的入口、对象、受影响的既有流程及确认过的最小改动边界，以及讨论过但本期维持现状或暂缓的行为。
- 业务规则。写明适用条件、规则优先级、状态变化和异常结果，只写本期涉及的内容。
- 验收场景。逐条写前置条件、操作和可观察的预期结果。每条影响验收的规则至少对应一个场景，相关既有行为补上回归场景。
- 依据。保留必要的原始需求及代码路径，供研发查证。草稿另列待确认项，已定稿的验收预期不写入未经确认的推测。

## 4. 按定稿范围开发

用户本次已要求实现时，定稿后按项目开发流程继续。仅要求澄清或出需求文档时，交付文档即可。涉及版本取舍时可用 `dwy-scope-guard`，涉及正式研发方案或测试表时按项目已有 Skill 交接，并沿用已确认的规则。

1. 将每条确认的规则对应到实际入口和现有实现，优先在原有实现位置做局部修改。改共用逻辑前，核对实际调用方，保留定稿范围外的业务行为和兼容约定。最小改动仍须覆盖全部已确认场景及其必要回归。
2. 实现中发现遗漏的入口、共用逻辑会改变其他行为，或范围与定稿冲突时，暂停受影响部分。用具体场景重新确认，更新文档后继续。
3. 交付前逐项审查 diff，按定稿中的最小改动边界复核每处变更，移除本次引入且无法说明必要性的改动。按实际入口验证已确认的场景及受影响的既有流程。
