# Python 版本与源码定位

1. 确认应用实际使用的解释器/虚拟环境、启动方式及工作目录；使用该解释器检查，不用系统 Python 代替项目环境。
2. 逐包查 `pyproject.toml`、实际锁文件（如 `uv.lock`）和项目已有的 path、workspace、Git、editable 或 source 配置。约束与锁定结果分别记录，未安装不能当作可运行。
3. 用该解释器的 `importlib.metadata.version("发行包名")` 核对已安装元数据，结合 `importlib.util.find_spec("导入名")`、实际模块位置与发行记录中的 `direct_url.json`（如存在）确认来源。发行包名与导入名可能不同；导入还可能被工作目录或 `PYTHONPATH` 遮蔽，不能只看版本号。
4. 在实际解析位置查公开声明、类型、实现及已有调用；editable/path 核对源码提交与相关未提交差异。元数据、模块 `__version__`、锁文件或导入路径不一致时先查清原因，不以一个版本字符串消除冲突。

实际环境源码优先于仓库 tag。已发布源码资料不足时，再查锁定的 Git 提交或该发行版本对应的 `<发行包名>@<版本>` tag，核对包子目录；不能用旁边仓库默认分支代替。没有可靠来源证据就说明未确认项，不猜 API，不为探测擅自安装或升级。

EAPI 的发行/导入名为 `dwyeapi`；其余包的导入名与源码路径见各自接入资料。每个包的来源与版本独立，不能根据 EAPI 版本推断认证、支付或通知包版本。

引用资料中的精确版本快照只证明该快照描述的契约；版本线只作导航，0.x 小版本也可能破坏兼容。按目标版本核对新增、删除及迁移，不把“shared”理解成所有历史版本都有的接口。

锁文件与环境不同步时，先区分任务要修复当前部署环境还是更新开发环境，再按授权使用项目已有同步流程并检查变更；不能自动升级来匹配文档。SDK/解释器、包声明下限、实际测试及部署验证分开报告，日志不输出凭据或带凭据的源地址。
