# dwy-payment

业务无关的服务端支付与退款能力。Python 3.11/3.12，微信普通商户APIv3 Native支付、回调核验、支付和退款资金记录；支付宝订单码作为可选extra保留。审核、管理员密码、业务订单、流量和权益由宿主实现。

## 安装与接入

```bash
python -m pip install 'dwy-payment==0.3.0'
# 已有支付宝业务可按需安装，不是微信接入的必需依赖。
python -m pip install 'dwy-payment[alipay]==0.3.0'
```

安装不初始化数据库、不挂载HTTP、不读取环境变量、不连接微信。商户凭据由宿主安全读取并构造 `WechatPayConfig`；不要在前端或客户端存放私钥。回调地址必须指向宿主提供的公网HTTPS接口，不是企业微信机器人地址。

```python
from dwy_payment import PaymentConfig, WechatPayConfig, create_payment
from dwy_payment.gateways.wechat_native import WechatNativeGateway


async def checkout(session_factory, *, merchant: WechatPayConfig, business_key: str):
    """宿主先提交自己的业务订单；business_key用于跨重试关联，不依赖请求会话。"""
    config = PaymentConfig(wechat=merchant)
    result = await create_payment(
        session_factory=session_factory, gateway=WechatNativeGateway(merchant), config=config,
        user_id="customer_1", amount_fen=1000, description="商品订单",
        idempotency_key=business_key,
    )
    return result
```

`user_id`只是宿主关联标识，不外键到用户表。`create_payment`先独立提交稳定意图再触网，同键同参数复用原单，同键不同参数拒绝；未知下单按原号和原截止重取二维码，不另建资金记录。微信官方说明支持[同订单号与原参数重新获取二维码](https://pay.wechatpay.cn/doc/v3/merchant/4054257695)。跨项目首期采用独立数据库或schema，业务订单号、支付单号、退款单号须分别保存映射，幂等键可在结果中帮助业务恢复关联。

金额使用整数分，只支持已实现的CNY范围。`PaymentService.create`保留旧同事务桥接接口，成功时不提交，要求宿主完成关联提交；它不提供独立指令的崩溃持久保证。没有幂等键时每次创建新支付；新接入使用上面的独立命令与稳定键。

宿主负责HTTP读取上限、路由与鉴权，使用 `PaymentService.handle_notify(headers, body)` 处理支付回调，使用渠道 `parse_refund_notify` 和 `RefundResultService.apply` 处理退款回调。退款结果更新与同事务钩子由宿主统一commit后再返回渠道成功应答。微信SDK验签、商户/应用与金额核对不能绕过；不自行构造已验证对象当作渠道证据。

## 退款与资金安全

`dwy_payment.refunds.commands.request_refund` 接受已持久支付记录、固定退款号和整数金额，显式提供独立会话工厂与微信网关。调用前业务方完成审核、密码确认、权益预留并提交；不要持有父业务锁跨独立资金命令。命令不接收管理员密码，也不判断退款政策。

金额占用包含已成功、处理中和待核对退款，仅明确关闭后释放；同一支付的本库退款意图串行核算，不能并发超退。网络超时保留同号查询，只有渠道明确不存在才同号同参数恢复发送，不能以新退款号重试。资金占用不能阻止商户后台在本库之外发起退款；外部退款观察后保守占用并查证，最终以渠道事实为准。

历史已退金额缺少可证明来源的退款明细时，新退款保持阻挡并要求人工核对；不凭金额相等推断两笔退款是同一笔。已存在同号意图仍允许查询恢复。

`RefundRecord`及其已核验状态是逐笔资金事实。`PaymentOrder.status/refunded_fen/refund_no`保留既有宿主业务投影兼容语义，不能将这些字段当作累计渠道到账证明；纯资金接入读取退款明细或资金事件，不调用 `mark_refunded` 推断到账。

`RefundResultService` 只登记核验状态，不自行提交；`reconcile_refunds` 由宿主每分钟调度，并显式提供会话工厂和网关。宿主负责任务生命周期与异常监控。退款“已受理”不代表成功，`ABNORMAL`保留占用并继续核对，不能据此再次付款或解除业务冻结。

## 可靠结果交付

付款成功及已核验退款结果与 `PaymentEvent` 同事务登记。`pending_payment_events(db, limit=20)` 可重放未确认事件；业务方幂等消费后，调用 `acknowledge_payment_event(db, event_id)`，与本地业务状态一起提交。消费失败不确认，下次再处理。该队列是单宿主消费组；并发读取可能重复，跨数据库消费需要本地去重，不能承诺恰好一次。

事件只包含资金字段和支付/退款标识，不包含商品或用户资料；业务方通过自己的映射找到订单。事件的版本用于处理乱序结果，不能让旧异常状态覆盖新成功。事件存储不设置自动删除，保留策略由宿主审计要求决定。

既有 `PaymentPaidHook` / `RefundResultHook` 是提交前同事务扩展点，可在宿主内维护同库业务或登记自己的持久任务；不得自行commit或执行外部网络副作用。兼容钩子失败会回滚本地资金投影和事件，等待渠道重试或查单恢复，不代表真实收款失败。需要独立提交资金事实的新接入使用空钩子并在提交后消费事件，无需实现统一商品处理器。

## 存储与迁移

使用SQLAlchemy异步会话，资金模型复用 `dwyeapi.database.Base`，无需 `dwy-shared`、`dwy-auth`、`app` 或 `quant_billing`。宿主通过Alembic显式安装/升级资金表，包内迁移入口与现有数据库升级说明随版本交付；不在导入或启动时自动改表。数据库连接取宿主配置，文档及日志不得写入凭据。

宿主在自己的Alembic revision中调用版本固定的辅助；Alembic只需安装在迁移环境，不是支付运行时强依赖：

```python
from alembic import op
from dwy_payment.migrations import downgrade_payment_tables, upgrade_payment_tables


def upgrade():
    # 新库创建三张资金表；已有完整0.2表新增幂等键、固定付款截止时间和事件表。
    upgrade_payment_tables(op)


def downgrade():
    # 受控退回0.2，保留原支付/退款记录，但会删除事件、幂等键和截止时间证据。
    downgrade_payment_tables(op)
```

首次创建也可显式调用 `create_payment_tables(op)`；`validate_payment_tables(connection)`只检查，不修改数据库。三张表是 `payment_orders`、`payment_refunds`、`payment_events`；辅助不会对共享Base执行 `create_all`，也不会创建用户、商品、审核或权益表。已有表缺列、类型/空值不符、缺少关键主键、唯一性或索引时直接失败，不会通过 `checkfirst` 假装迁移成功。唯一约束的自动命名和默认表达式的等价数据库表示不作脆弱比较。

现有宿主应在自己的最新revision之后新增升级revision，保留历史revision及原表数据，不重建或清空资金表，也不回填旧付款事件。0.3.0迁移快照随版本固定，后续结构变化应增加新的迁移步骤。辅助需要真实连接进行schema核对，仅支持SQLite/PostgreSQL在线迁移，显式拒绝离线 `--sql`；数据库驱动由宿主选择并安装。

旧记录的 `idempotency_key` 与 `expires_at` 均保持NULL，不猜测原商户付款截止时间。新支付意图必须固定保存截止时间，重试沿用原值；不能根据当前 `timeout_seconds` 配置重新计算旧请求的渠道 `time_expire`。

服务构造函数支持显式配置与钩子；`runtime.configure`、`configure_refunds`只是单应用进程的便利装配，默认不读取宿主数据库。退款独立会话必须显式注入。同进程多应用应使用显式服务依赖，不重复覆盖全局装配；本版不提供完整多租户资金服务。

## 验收边界
