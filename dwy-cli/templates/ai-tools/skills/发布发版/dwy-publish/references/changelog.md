# 按工程维护 CHANGELOG

先识别版本边界：根据构建配置、版本来源、已有 changelog、tag 和项目约定确定独立工程；共享版本的模块遵循仓库既有规则。用户指定范围优先，不将无关改动纳入本次版本。

逐工程检查上次对应 tag 后的提交和本次相关未提交变更，分析共享代码对各工程的影响。列出工程、变更、版本来源、changelog 路径、tag 和是否发布。无变更的工程不写空版本；已记录的内容不要重复添加。

需要更新的工程各自维护 changelog：优先使用现有路径、分类和语言；没有时在工程目录创建 `CHANGELOG.md`，遵循仓库约定。记录该工程本次实际变更，不混入其他工程。用户要求仅管理版本时也要记录，不以是否发布为条件。

每个版本条目的标题必须同时包含明确版本号和 `YYYY-MM-DD` 日期，例如 `## [1.2.3] - 2026-11-02`；版本串与该工程版本来源及 tag 中的版本串一致。日期表示本次版本记录日期，不以实际发布为前提，也不等到发布时再补。禁止使用 `Unreleased`、`[Unreleased]` 或“未发布”等占位标题；即使仓库原格式缺少版本号或日期，本次新增或更新的条目也必须补齐。已有占位条目中属于本次的变更，归入明确版本号和日期的条目，不继续保留为占位记录。按现有分类和语言写清用户可理解的变更；仓库已有可靠生成工具时可复用并检查结果。

每次部署或发布前，AI 自动检查目标工程的 changelog 是否覆盖拟发布变更，并与版本和 tag 指向的提交一致。已完整覆盖时复用现有记录，不重复添加条目或修改记录日期，即使该版本尚未部署到目标环境；缺失时自动补齐，不逐项要求用户确认。补齐和校验完成前禁止部署或发布。工作区干净不代表变更已被版本记录；与线上版本存在差异也不代表需要新建版本。部署结果按项目流程留存，不作为新的产品变更重复写入 changelog。
