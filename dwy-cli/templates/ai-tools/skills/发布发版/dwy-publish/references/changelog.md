# 按工程维护 CHANGELOG

先识别版本边界：根据构建配置、版本来源、已有 changelog、tag 和项目约定确定独立工程；共享版本的模块遵循仓库既有规则。用户指定范围优先，不将无关改动纳入本次版本。

逐工程检查上次对应 tag 后的提交和本次相关未提交变更，分析共享代码对各工程的影响。列出工程、变更、版本来源、changelog 路径、tag 和是否发布。无变更的工程不写空版本；已记录的内容不要重复添加。

需要更新的工程各自维护 changelog：优先使用现有路径和格式；没有时在工程目录创建 `CHANGELOG.md`，遵循仓库约定。记录该工程本次实际变更，不混入其他工程。用户要求仅管理版本时也要记录，不以是否发布为条件。

每个新版本使用仓库既有可识别的标题格式，标题版本串与该工程版本来源及 tag 中的版本串一致。按现有分类和语言写清用户可理解的变更；仓库已有可靠生成工具时可复用并检查结果。

部署新代码前 AI 自动检查目标工程的 changelog 是否覆盖拟部署变更，并与版本和 tag 指向的提交一致；缺失时自动补齐，不逐项要求用户确认。补齐和校验完成前禁止部署。
