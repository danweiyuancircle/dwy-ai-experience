# iOS 邮箱密码登录注册组件：需求分析

日期：2026-10-21。状态：需求与源码分析，尚未进入实现。本轮不修改产品代码、不迁移数据库、不发布。

## 已确认的需求

- 邮箱就是登录账号，不增加独立用户名。
- 注册时填写邮箱、密码，接收邮箱验证码并完成验证。
- 注册完成自动登录，不再返回登录页重复输入。
- 后续通过邮箱＋密码登录，日常登录不要求邮件验证码。
- 活跃使用的用户尽量长期保持登录，避免按固定月数反复输入密码。
- 封装成共享 iOS 组件，由后续多个 App 复用，ADBox 是接入方。
- 本轮聚焦基本认证。Google 登录、业务数据同步、跨端购买权益不作为本次新增范围；保留已有 Google 实现，不删除或改写其他产品的行为。

这些要求包含三个交付层：可复用 SwiftUI 页面、客户端会话管理、服务端账号及会话协议。只交付表单不能兑现自动登录和长期登录。

## 推荐的最小用户流程

| 页面 | 内容 | 成功结果 |
|---|---|---|
| 登录 | 邮箱、密码、密码显隐、登录、去注册、忘记密码 | 安装后端会话并回到宿主 |
| 注册 | 邮箱、密码、发验证码、验证码输入、注册 | 验码、创建账号、签发会话，直接登录 |
| 找回密码 | 邮箱、验证码、新密码 | 重置密码并返回登录，旧会话失效 |

找回密码建议随首版一起提供：采用密码登录且长期免登录后，用户很容易忘记密码；可复用注册的验证码输入与重发组件，无需增加另一套认证方式。重置密码与注册自动登录区分处理，重置后通过新密码重新登录。

不增加手机号、独立用户名、头像设置、社交账号绑定、账号中心或多因素认证页面。登录成功后的数据导入、付费判断和同步交给宿主。

发送注册验证码只提交邮箱，不把密码发送给邮件服务。最终提交时校验邮箱、密码、验证码与 challenge，再创建已验证账号。密码只短暂存在页面内存和经 HTTPS 发送的认证请求中，不写 UserDefaults、Keychain、日志或分析事件。

若账号创建已成功但自动安装会话失败，界面应说明注册已完成，并允许登录；不能引导用户重复注册。

## 共享仓库的当前情况

仓库正在进行 Apple 代码目录迁移，工作区已有大量未提交变更；当前根 `Package.swift` 已指向 `ios/`。实施时保留这些变更，不能按旧目录写回或提交无关迁移文件。

| 能力 | 当前源码 | 与新需求的差距 |
|---|---|---|
| 认证协议与数据模型 | `ios/Sources/Shared/AuthCore/AuthTypes.swift` | `AuthBackend` 目前只有 Google 登录、刷新和退出 |
| 客户端 HTTP | `ios/Sources/Shared/AuthCore/AppCloudAuthClient.swift` | 缺邮箱密码登录、注册、发码、密码重置 |
| 会话状态管理 | `ios/Sources/Shared/AuthCore/AuthSessionStore.swift` | 构造时必须注入 Google provider，`signIn()` 也固定走 Google |
| Keychain | `ios/Sources/Shared/AuthCore/KeychainRefreshTokenStore.swift` | 可继续保存应用 refresh token，不保存密码 |
| 服务端认证 | `modules/auth/backend/src/dwy_app_auth/service.py` | 用户登录目前依赖 Google subject，会话期限固定 |
| 服务端表结构 | `modules/auth/backend/src/dwy_app_auth/storage.py` | `google_subject` 非空，缺密码凭据、已验证登录邮箱 |
| 密码散列 | `backend/src/dwyeapi/security.py` | 已有 bcrypt 工具，可复用，但要检查密码 UTF-8 字节上限和异步调用方式 |
| 邮件 | `backend/src/dwyeapi/providers/email/` | 已有 Resend；仍需认证用途隔离、原子核销与限流 |

已有会话层的并发刷新合并、旧请求失效、Keychain 保存失败处理和退出撤销应保留。邮箱登录不能另起一套 token 管理逻辑。

## 组件拆分与落点

建议复用现有 `AuthCore`，新增一个 iOS SwiftUI 产品 `AuthUI`，不另建一套认证框架。

| 位置 | 职责 |
|---|---|
| `ios/Sources/Shared/AuthCore/` | 邮箱认证协议、请求模型、后端客户端、统一会话恢复/刷新/退出 |
| `ios/Sources/iOS/AuthUI/` | 登录/注册/找回密码页面与流程状态，首版面向 iOS |
| `ios/Tests/AuthCoreTests/` | 认证协议与会话回归测试 |
| `ios/Tests/AuthUITests/` | 表单状态、交互和无障碍验收；具体测试目标随实施规格确定 |
| `modules/auth/backend/src/dwy_app_auth/` | 邮箱密码账号、密码验证、注册/重置流程、会话策略 |
| 根 `Package.swift` | 导出 `AuthUI`，继续让核心认证与 Google 适配独立 |

公共 API 尽量只有一个登录流程入口，例如 `AuthFlowView`。宿主提供应用名称、品牌视觉、认证客户端、协议链接和完成/取消处理；内部切换登录、注册、找回密码，不要求每个 App 自己拼接表单。

可复用性来自统一流程和协议，而不是暴露每一个按钮的布局参数。首版支持中文/英文、动态字体、密码管理器自动填充、验证码自动填充、密码显隐、粘贴、键盘收起、请求中防重复提交和可恢复错误。

`AuthCore` 继续使用 Foundation 和现有共享依赖；Google provider 成为独立登录入口依赖，普通邮箱密码宿主不必构造 Google provider。保留现有 Google 调用的兼容路径，不要求当前消费者立即迁移。

本轮先提供 iOS UI；会话核心保持 iOS/macOS 共用，后续 macOS 可以复用认证与长期登录协议，再加平台页面。无需为了本轮同时完成 macOS UI。

## 长期登录的实际含义

目标是用户不用反复输入密码，同时保留撤销能力。建议用现有 access/refresh 机制实现，不延长 access token 到数年，也不保存密码自动重登。

| 策略 | 建议初值 | 行为 |
|---|---|---|
| access 有效期 | 15 分钟 | 保留当前量级；到期前按需静默刷新 |
| refresh 空闲期限 | 180 天 | 成功刷新后，从当前服务端时间重新顺延 |
| 固定强制重登周期 | 首版不设置 | 活跃用户不会仅因“距首次登录很久”被退出 |
| 主动失效 | 立即 | 退出、密码重置、设备撤销、删号、封禁等使对应会话失效 |

180 天是建议的产品参数，不是标准要求。不同应用通过服务端会话策略配置选择；共享库不能改变策略后让所有现有应用自动采用长期登录。

“活跃”要具体定义：前台使用且能够与认证服务成功通信。ADBox 大量功能只连接局域网盒子，不能只靠云同步请求触发续期。应用启动/进入前台时检查会话，需要时刷新；业务 API 请求前复用相同刷新入口。不通过后台定时器人为维持永久在线。

在未过期时，前台可按日级间隔续期，避免只使用局域网功能的用户长期不联系认证服务；access 到期且确有认证请求时仍须刷新。成功时间和是否需要刷新应由统一会话层管理，多个页面不各自发刷新请求。

连续离线超过空闲期限后，需要联网重新登录。短暂断网、服务器临时失败、取消请求不等于凭据已永久失效；不能因此删掉 Keychain。宿主的本地离线能力也不应被临时网络错误阻断。

这里有明确取舍：不设置固定会话总寿命更贴近本次长期免登录目标，但被盗 refresh token 也可能在持续使用时续期。需要保留轮换、重放检测、设备撤销和敏感操作重新验证。OWASP 建议区分空闲、绝对和轮换期限；本方案不宣称满足其全部会话期限建议。[OWASP 会话管理](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)

### 当前后端必须调整的地方

`modules/auth/backend/src/dwy_app_auth/service.py` 当前登录时设置 `refresh_expires_at = now + 30 * 86400`，刷新只更新 access 的到期时间，没有顺延 refresh。

同文件还有 `MAX_REFRESH_HISTORY = 4096`，触顶会返回“请重新登录”。如果只把 30 天改成 180 天，活跃用户仍可能因刷新历史配额被退出。

因此应一并处理：

1. 增加可注入的会话策略，区分固定总期限和滚动空闲期限。
2. 事务内校验旧 refresh，并原子轮换 token、更新滚动期限。
3. 旧 token 摘要按它自身有效窗口保留，清理过期记录；复核历史配额和正常刷新频率，不能把固定累计次数变成隐含重登周期。
4. access 仍检查用户状态、会话撤销和 refresh 有效性，不能只看客户端日期。
5. 保持并发刷新只执行一次。明确服务端已轮换但响应丢失、应用在保存 Keychain 前退出的处理策略；一次性 refresh 不能靠无限重试解决，否则会触发已有重放撤销。

## 服务端账号与邮件边界

最小变更可以新增邮箱密码凭据表：稳定 `user_id`、规范化登录邮箱、密码散列、邮箱验证时间，登录邮箱在同一 `app_id` 内唯一。`auth_users` 继续表示用户，现有展示邮箱不能直接充当唯一登录凭据。

同时移除“所有用户必须有 Google subject”的假设，保留已有 Google 用户 UUID 和业务关联。首版无需泛化成完整第三方身份平台，也不按相同展示邮箱静默合并历史 Google 账号；已存在账号的处理要明确返回可操作结果。

密码散列复用 eapi 已有成熟能力，不能手写算法。现有 bcrypt 按 UTF-8 字节处理，实施前须定义前后端一致的长度政策，超限明确拒绝，不能截断密码；散列验证应通过有并发上限的工作线程执行，避免阻塞异步 API。

Resend 继续由 eapi 发信，邮箱凭据与模板配置留在服务端。注册码和密码重置码按应用、用途、邮箱及 challenge 隔离，原子核销，发送和验证都有限流。密码登录不调用 Resend。

登录失败使用统一提示，避免通过错误差异枚举账号；密码重置后撤销旧会话。密码校验、账户恢复和凭据变更的边界参考 [OWASP 认证指南](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html)。

app-cloud 负责配置注入、Redis/邮件资源生命周期和应用独立迁移；共享 UI 不读取 Resend 配置。共享组件也不意味着 ADBox、Quadrant、RightFlow 自动共享用户和密码。

## 建议交付顺序与验收

1. 先确定本分析中的基本流程和长期会话策略，形成实施规格。
2. 共享后端补邮箱凭据、注册自动签发会话、登录、密码重置和可配置滚动会话；保留 Google 消费者的既有行为。
3. 扩展 AuthCore，完成普通邮箱宿主无需 Google provider 的会话流程。
4. 新增 AuthUI 和可运行示例，验证注册直接进入已登录态、重启恢复与错误恢复。
5. app-cloud 装配服务，再由 ADBox 接入；本轮不同时开展业务数据同步。

完成标准包括：注册验证码过期/重放/并发；重复邮箱注册；正确/错误密码；注册成功自动登录；密码重置撤销旧会话；模拟跨月活跃刷新仍登录；超过空闲期限需重登；刷新历史不会令正常活跃用户提前退出；断网不清凭据；并发刷新、响应丢失、Keychain 保存失败、退出后的旧回调；应用间账号隔离；旧 Google API 与固定期限会话回归。

本轮只核查源码和需求，没有运行这些实现验收。当前工作区原有迁移变更保持不动。
