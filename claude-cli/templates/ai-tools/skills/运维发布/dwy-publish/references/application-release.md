# 应用部署流程

适用：发布目标是某个服务、站点、容器、镜像、二进制或线上环境。

## 主流程

流程骨架：

1. `bump`
2. `CHANGELOG`
3. `build`
4. `deploy`
5. `verify env`

## 1. 判断是否需要 bump

不要一上来改版本号。先判断这次部署是否需要 bump：

- **需要 bump**：带显式版本号的应用发布、镜像 tag 升级、二进制版本升级、对外可见版本变化
- **可不 bump**：纯重发、仅重跑 workflow、仅补环境配置、仅回滚到已有构建
- **拿不准**：调用 `dwy-semver` 决定升级位和新版本号

如果需要 bump：

1. 读取当前版本
2. 算出新版本号
3. 修改版本文件、镜像 tag 或其他版本来源

不要用会自动 commit 的版本命令。直接编辑版本来源，保持提交边界可控。

## 2. 写 CHANGELOG

判断完 bump 后，再处理 `CHANGELOG`。

- **需要正式版本发布**：必须写
- **仅部署且无版本变化**：按项目约定决定是否跳过

处理顺序：

1. 找上一个 release tag
2. 查看 `git log <last-tag>..HEAD --oneline`
3. 按 `feat` / `fix` / `refactor` / `chore` 分组
4. 写入 `CHANGELOG.md` 或项目指定的 release notes 文件

如果仓库已有自动生成命令，优先使用；没有再手写。

`CHANGELOG` 未完成，不继续。

## 3. 确认测试已完成并执行 build

本流程不重复跑测试，只确认当前变更已经过项目要求的测试。

然后执行 build，确保发布产物可生成。

构建失败则停止。

## 4. 决定 deploy 入口

不要把 deploy 写死成某种命令。根据仓库上下文自行判断：

- 是推镜像、发二进制、跑部署脚本，还是触发 CI/CD
- 是 GitHub Actions、其他 CI，还是本地脚本
- 是否需要先 commit、tag、push 才能触发部署

判断标准示例：

- 存在明确 workflow、触发方式、部署 job，且部署由 CI 完成 → 走 CI
- 仓库里有明确部署脚本、命令或运维入口 → 走本地部署流程

## 5. 执行 deploy

如果是 CI 驱动：

1. 提交 release 相关文件
2. 按项目规则创建 tag；如果不是 tag 触发，则按配置触发 workflow
3. 推送分支和 tag
4. 观察部署运行状态直到成功或失败

如果是本地驱动：

1. 提交 release 相关文件
2. 按项目规则创建 tag
3. 推送分支和 tag
4. 执行本地部署命令

失败则停止，并给出失败阶段和关键报错。

## 6. verify env

部署完成后，按仓库约定验证环境已生效。可用信号包括：

- 健康检查
- 版本接口
- 页面访问
- 运行日志
- 镜像 tag
- 发布平台状态
- 其他项目约定信号

验证失败，部署不算完成。

## 禁止事项

- 禁止跳过“是否需要 bump”的判断
- 禁止先部署后补 `CHANGELOG`
- 禁止把环境验证替换成包仓库验证
