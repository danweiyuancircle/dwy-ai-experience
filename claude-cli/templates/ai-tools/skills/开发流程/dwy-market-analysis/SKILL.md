# dwy-market-analysis · 需求 & 市场分析

跟用户一起把「这是不是真需求」想清楚，再用 WebSearch 扒市场和竞品，给差异化建议和「做不做」结论。伪需求和红海早杀，省掉后面全部白干。

## 运行模式

上下文自适应，两种调用方式：

- **单独调用（默认）**：用户直接丢一个想法让你分析。从用户那句想法起步；产物落用户指定位置，没指定就用 `./market-analysis.md` 或问一句；**不读写 STATE.md、不依赖 `docs/0to1/`**。做完跑下方「门」即结束，不自动转入别的 skill。
- **流水线调用**：`dwy-0to1` 通过 Skill 工具调用，指令含「流水线模式」+ 落盘路径（如 `docs/0to1/01-market.md`）。按指令落盘；照常跑「门」；**STATE 记账与进入下一步由 dwy-0to1 负责，本 skill 不碰 STATE.md**。

## 怎么做

两部分：先**协作对话**把需求想清，再叠**市场调研**拿证据。

### 一、协作对话（一次一问，温和把需求摸清）

不是审问，是陪用户把模糊想法捋成清晰需求。纪律：**一条消息只问一个问题**。

1. **探索上下文**：先弄清想法到底是什么、给谁用、解决什么痛点。当前项目有相关文件/代码就先看一眼。
2. **评估范围，先拆再钻**：想法其实是好几个独立子系统（「做个平台，带聊天 + 存储 + 计费 + 分析」）→ **立刻指出来**，帮用户拆成独立部分，问清谁先做。别急着钻某一块的细节，那等于给一个该拆的项目修地基。
   - ❌ 用户说「做个带社交的电商平台」→ 直接问「商品详情页要展示哪些字段」
   - ✅ 先说「这其实是电商 + 社交两个子系统，建议先把电商主链路做通，社交后置。先聚焦电商对吗？」
3. **一次只问一个问题**（关键纪律）：
   - 一条消息**只问一个**，别一次甩五个。用 `AskUserQuestion`，**优先做成选择题**（比开放题好答），开放题也行。
   - 聚焦理解三件事：**目的 / 约束 / 成功标准**。
   - 一个话题没问透，拆成多条消息分次问，别塞进一条。
   - ❌ 「目标用户是谁？预算多少？要支持哪些平台？什么时候上线？」（一次四问）
   - ✅ 「先定目标用户——主要给哪类人用？」（一次一问，等答完再问下一个）
4. **提 2-3 个差异化方向**：摸清需求后，给 2-3 个不同切入方向，每个带取舍。**亮明推荐哪个、为什么**，别都列出来让用户自己选。
5. **分段呈现、逐段确认**：把结论拆成几段（需求理解 / 真需求判断 / 差异化建议），一段一段摆，每段问一句「这样对吗」。哪段不对就回去改，别一口气甩完整篇。

### 二、市场 & 竞品调研（WebSearch，对话法没有、这步独有）

对话摸清需求后，拿外部证据验证：

1. **WebSearch 查这个领域**：有哪些现成产品 / 竞品、它们怎么做、市场大概多大、是蓝海还是红海。多关键词搜（中英文都搜，竞品官网 / 测评 / 讨论区）。
2. **真需求判断**（结合用户回答 + 市场证据）：给三选一结论，**说清依据**——
   | 结论 | 什么情况 |
   |------|---------|
   | 真需求 | 痛点真实、有人在为它付费/费劲找替代，市场有空间 |
   | 伪需求 | 想当然的「应该有人要」，查不到真实付费意愿或替代行为 |
   | 需要收窄 | 方向对但太大/太泛，得砍到一个具体人群或场景才成立 |
3. **差异化建议**：值得做的话，差异化从哪个角度切——功能 / 人群 / 定价 / 体验，挑一两个能立住的，别样样都想赢。

## 产物

落盘市场分析文档（单独模式默认 `./market-analysis.md`；流水线模式按编排器给的路径，如 `docs/0to1/01-market.md`）。顶部 frontmatter：

```markdown
---
status: done          # 落盘且过门后才填 done；过门前 awaiting-approval
updated: <date +%Y-%m-%d>
---
```

正文必含八块：

| 块 | 内容 |
|----|------|
| 需求理解 | 想法是什么、给谁用、解决什么痛点（对话捋出来的） |
| 真需求判断 | 真 / 伪 / 收窄 三选一 + **依据**（用户回答 + 市场证据） |
| 市场情况 | 领域多大、蓝海还是红海、WebSearch 拿到的关键数据 |
| 竞品清单 | 表格：谁 / 怎么做 / 优 / 劣 |
| 差异化建议 | 从哪个角度切（功能/人群/定价/体验），为什么这个角度立得住 |
| 核心能力/最大技术风险 | 一句话点出最该被技术可行性验证的技术核心（供 dwy-tech-feasibility 锚定调研对象） |
| 硬约束识别 | 合规 / PII / 实时性 / 规模水位等会反向决定技术选型的硬约束；没有就写「无」 |
| 做不做建议 | 明确结论 + 一句话理由 |

## 门（过门确认）

落盘后先**自己核一遍**（先验证再声称）：八块齐了吗、真需求判断有依据吗、竞品清单不是空表吗、核心能力/最大技术风险点出来了吗、硬约束识别过了吗（没有也要明写「无」）。核完再声称完成，别说「应该写好了」。

然后 `AskUserQuestion` 把**「做不做 + 怎么差异化」**摆给用户，问：

> 按这个方向继续 / 调整方向 / 放弃？

用户要调整 → 回去改文档重新摆。

## 边界 / 禁止

- **一次只问一个问题**——这是这步的命脉，一条消息甩多问直接破坏对话节奏。
- **不用对抗式六问诊断**——温和协作，不是审问用户的想法值不值得做。
- **真需求判断必须带依据**——不能只写「这是真需求」，要有用户回答 + 市场证据支撑。
- **竞品清单不许是空表**——查不到竞品本身就是信号（要么蓝海要么伪需求），写清是哪种。
- **做不做建议必须给明确结论**——不和稀泥、不「视情况而定」。该劝退就劝退。
- 这步**只分析判断，不写任何代码、不碰技术选型**（那是 dwy-tech-feasibility / dwy-spike 的事）。
