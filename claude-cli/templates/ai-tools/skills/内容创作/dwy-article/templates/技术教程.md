适用场景: 教别人把某个东西搭起来 / 跑通——内网穿透、部署、环境配置、工具搭建等，读者照着步骤要能复现

# 技术教程模板

定位：**照着零跳步就能复现**。重操作、轻原理——读者要的是「跟着做能跑通」，不是听一堂原理课。原理点到为止就行。

技术教程不要写「正确的废话」。能影响读者动作的才写：检查命令、下载入口、关键选项、必要路径、预期输出、真实坑。下载目录、安装向导常识、抽象背景、重复验证、泛泛提醒，删掉。

四个固定章节（`##`），按顺序；实操下的子项（`###`）按需取舍——「真没有」才省，不是图省事，操作步骤不能省、验证别轻易省。

```
# 标题：直接说清做什么（如「用 frps 把群晖 NAS 暴露到公网」）

## 场景
要解决什么问题 / 什么场景用得上 / 我自己为什么要搞这个。把读者代入「对，我也卡在这」。最好从读者实际看到的命令、报错、页面、现象切入，比如 `npm install xxx`、`npx xxx`、`pip install xxx`，不要只从概念切入。

## 技术简介（可选，没有可不写）
1-2 段说清这次用的主角是什么、解决什么——让读者动手前知道自己在装 / 用什么。点到为止，别展开讲原理。是开源库 / 工具就附一句仓库或官网链接，方便读者深挖。不需要背景就整节删掉。

## 实操
### 开始前准备（可选）
把前置条件一次性列全，读者照着先备齐：系统 / 软件版本 / 下载链接 / 需要的账号 / 要放行的端口 / 依赖。漏一项，读者就会卡在中途。没有前置就省掉。

### 操作步骤
教程的核心，不能省。每步先一句说这步在干嘛，再给**完整、可直接复制**的命令或操作：
- 命令不截断、不省略，含真实路径和文件名
- 凡要读者替换的，用占位符写清并标注「改成你自己的 X」（如 `serverAddr = "你的公网IP"`）
- 给出预期结果：看到什么输出 / 什么现象，才算这步成了
- 零跳步——不许出现「配置一下 xxx」这种含糊带过，每步都要能照着做出来
- 先检查当前状态，再安装缺失项；已有就跳过，别默认让读者重装
- 按读者路径组织步骤：Windows 的检查和安装放一起，macOS 的检查和安装放一起；不要为了结构工整把相关动作拆散
- 图形安装只写下载 URL 和关键选项；「打开安装包、一路同意、默认路径」这种常识一句带过

### 踩坑提醒（可选）
有坑才写。每个坑写清三件事：现象（报什么错 / 什么表现）→ 原因 → 怎么解，让读者对照自己卡在哪。坑多、过程曲折，单独开一篇『踩坑排错实录』更合适。

### 验证（可选）
怎么确认整套通了——一条命令或一个现象。除非这事真没法验证，否则别省：读者最想知道的就是「我做对了没」。

## 收尾总结
一句：到这就能用了。可选加一句取舍或延伸（什么场景用别的方案更省事 / 还能怎么扩展）。不复述全文、不升华。
```

省的是原理，不是步骤。一个没碰过的人照着这篇，要能真跑通。
