# dwy-spike · 丢弃式技术实测

写一个最简版本只验证核心流程跑不跑得通，让用户真机测。这步**只产结论，不产代码**——spike 是丢弃式 POC，用完即弃。

## 运行模式

上下文自适应，两种调用方式：

- **单独调用（默认）**：用户直接让你验证某技术行不行。从用户描述的技术风险点起步；spike 代码放 `./spike/`、结论落 `./spike-result.md`（或用户指定）；**不读写 STATE.md、不依赖 `docs/0to1/`**。做完跑下方「门」即结束。
- **流水线调用**：`dwy-incubator` 调用，指令含「流水线模式」+ 前序产物路径（技术可行性）+ 落盘路径（代码 `docs/0to1/spike/`、结论 `docs/0to1/03-spike-result.md`）。**STATE 记账（含 target_platform 记录）由 dwy-incubator 负责，本 skill 不碰 STATE.md**。

## 输入（验什么）

- 单独模式：从用户描述拎出要验的技术风险点；不清楚就问一句「主要担心哪个环节跑不通」。
- 流水线模式：读编排器给的技术可行性产物，看「是否实测建议」和选定方案，确定要验的风险点。

## 怎么做

1. **先确定做哪一端**（决定 spike 写哪个平台）。用 `AskUserQuestion`：

   > 这个产品主要做哪一端？iOS / 安卓 / 桌面 / Web

   端没定，spike 写哪个平台都是赌。（流水线模式下编排器会把选定的端记进 STATE。）

2. **写最简单的 spike（探针）**：
   - 只验**核心流程跑不跑得通**——那个技术风险点（新算法能不能算对、第三方 API 行为符不符合预期、性能够不够、硬件能不能集成）。
   - 砍到不能再砍：一条主链路，没 UI 美化、没边界处理、没配置项、没错误兜底。
   - 能验证流程就行，**别追求质量、别写测试**。

3. **代码隔离在 spike 目录**（单独 `./spike/`、流水线 `docs/0to1/spike/`）：
   - 全部 spike 代码只放这个目录，跟正式工程隔开。
   - 目录里放个 `README` 一行字标清：**这是丢弃式 POC，正式开发不继承这里的代码。**

4. **让用户真机测核心流程**：
   - 把 spike 跑起来，让用户在**真实环境/真机**上走一遍核心流程。
   - 收集结果：通了 / 没通 / 哪卡住了 / 性能数字。

## 产物

落盘实测结论（单独默认 `./spike-result.md`；流水线按编排器给的路径）。frontmatter：

```markdown
---
status: done
updated: <date +%Y-%m-%d>
---
```

正文**记结论，不是代码**：

| 块 | 内容 |
|----|------|
| 验的是什么 | 这次 spike 要验证的核心流程/技术风险点 |
| 端 | iOS / 安卓 / 桌面 / Web |
| 实测结论 | 核心流程**通 / 不通**，真机表现、关键性能数字 |
| 踩了什么 | 实测中暴露的坑、限制、意外行为 |
| 技术裁决 | **确认可行 / 不可行 / 要换方案**，一句话定性 |

❌ 把 spike 源码贴进结论文档
✅ 只写「核心流程通了，端到端 1.2s，第三方 API 偶发 429 需退避重试」这类结论

## 门（过门确认）

落盘后先**自己核一遍**（先验证再声称）：结论是「通/不通」的明确定性吗、技术裁决给了吗、没把代码当结论塞进去吧。

然后 `AskUserQuestion` 摆**实测结论**，问：

> 技术验证通过，可以往下走？还是没通过，回去换方案？

## 边界 / 禁止

- **spike 是丢弃式**——只验流程，验完就扔。正式开发（dwy-tdd-dev）**只继承结论、不继承 spike 代码**。
- **TDD 铁律**：正式开发没有失败测试不写生产代码。spike 代码没测试、没质量，**绝不能**当成开发起点直接往上加。
- **spike 不写测试、不追求质量**——能跑通核心流程就够，别在这步过度工程。
- **产物记结论不记代码**——结论文档里写「行/不行/为什么」，源码留在 spike 目录，不进结论文档。
- 选端是**第一件事**，必须先问再写 spike。
