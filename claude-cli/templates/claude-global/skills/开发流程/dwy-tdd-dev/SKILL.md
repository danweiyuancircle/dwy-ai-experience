# dwy-tdd-dev · 逐版本 TDD 开发

把一个版本（或一个功能）落地：写实施计划 → TDD 开发 → 每个 Task 两阶段审查 → 整版本 code-review 修到全绿 → 完成前验证。

> 代码进项目源码，**不进 `docs/0to1/`**；只有实施计划落 `plans/`。

## 运行模式

上下文自适应，两种调用方式：

- **单独调用（默认）**：用户直接让你按 TDD 实现某功能/版本。从用户描述或指定的需求文档起步；实施计划落 `./plans/<slug>.md` 或用户指定位置，代码进项目源码；**不读写 STATE.md、不依赖 `docs/0to1/`**。一个版本走完跑下方「完成前验证」并给交付报告。
- **流水线调用**：`dwy-incubator` 调用，指令含「流水线模式」+ 前序产物路径（版本规划 + 细 PRD）+ 实施计划落盘路径（如 `docs/0to1/plans/vN-<slug>.md`）+ 本次要做哪几个版本。**STATE 的版本进度记账由 dwy-incubator 负责，本 skill 不碰 STATE.md**。

## 输入

- 版本规划：确认要做哪个/哪几个版本、各版本包含什么、验收标准。
- 细 PRD：页面 / 功能的事实依据，写实施计划时对着它。
- 技术方案、端：对齐技术栈。
- 单独模式：用户没给 PRD/版本规划就先问清这次要实现什么、验收标准是什么。

## 总流程（对要做的每个版本循环）

```
版本 vN：
  1. 写实施计划 → 落 plans/vN-<slug>.md
  2. 逐 Task TDD 开发（红-绿-重构）
     每个 Task 做完 → 两阶段审查（spec → code）→ 有问题回修再审 → 全绿才算这个 Task 完成
  3. 整版本所有 Task 完 → 版本级 code-review → 修完所有问题（全绿）
  4. 完成前验证（真跑测试 / 构建，拿到证据）
  5. 进下一个版本
全部版本完 → 给用户交付报告
```

## 1. 写实施计划

为当前版本写一份**假设执行者完全不懂这个代码库**的计划：列清每个 Task 动哪些文件、给出实际代码、怎么测、按 TDD 拆成 checkbox 步骤。DRY、YAGNI、TDD、频繁提交。

套 `templates/impl-plan.md`：

- 开头：**Goal**（一句话）/ **Architecture**（2-3 句方案）/ **Tech Stack**（关键技术栈，对齐技术方案）。
- 再拆**一串 Task**，每个 Task 颗粒度「小到一步只做一个动作（2-5 分钟）」：
  - `Files:` — 列清 Create / Modify（带行号）/ Test 的**确切路径**。
  - 5 个 checkbox 步骤，强制 TDD 顺序：
    1. 写失败测试（贴实际测试代码）
    2. 运行看到失败（给确切命令 + 预期失败输出）
    3. 最小实现（贴实际实现代码）
    4. 运行看到通过（给确切命令 + 预期 PASS）
    5. commit（给确切 `git` 命令）

**禁止占位符**——以下都是计划失败，绝不允许：

- ❌「TODO」「待补充」「类似 Task N」「加适当的错误处理」「为上面写测试」（不给实际代码）
- ❌ 引用了任何 Task 里都没定义过的类型 / 函数 / 方法
- ✅ 每个改代码的步骤都贴出完整代码；每个运行步骤都给确切命令 + 预期输出

写完自检：① 版本验收标准每条都能指到某个 Task ② 全文搜一遍上面的占位符红旗 ③ 后面 Task 用的类型 / 方法名和前面定义的一致（Task 3 叫 `clearLayers()`、Task 7 叫 `clearFullLayers()` 就是 bug）。有问题就地改。

落盘 `plans/vN-<slug>.md`，frontmatter：

```
---
status: in-progress
updated: <date +%Y-%m-%d>
version: vN
---
```

## 2. TDD 开发（红-绿-重构铁律）

```
没有失败测试，不写一行生产代码
```

每个 Task 按红-绿-重构走，**一步都不能省**：

| 阶段 | 动作 | 强制 |
|------|------|------|
| 🔴 RED | 写一个最小失败测试（测真实行为，别测 mock） | — |
| 🔴 验证 RED | 跑测试，**亲眼看到它失败** | 失败原因必须是「功能没实现」，不是手滑 typo。测试直接过了 = 测错了东西，重写 |
| 🟢 GREEN | 写**最小**实现让它过（别提前加没要求的功能） | — |
| 🟢 验证 GREEN | 跑测试，**亲眼看到它通过**，且其它测试不挂、输出干净无 warning | 没看到通过不算过 |
| 🔵 REFACTOR | 绿了之后才重构：去重、改名、抽 helper，保持全绿 | 重构不加新行为 |

**核心原则**：没亲眼看测试失败，就不知道它测的是不是对的东西。

常见借口都是自欺，一律「删掉，重来」：

- 「先写代码回头补测试」→ 后补的测试一上来就过，证明不了任何东西
- 「太简单不用测」→ 简单代码也会坏，写个测试 30 秒
- 「我手动测过了」→ 手动测不成系统、不可复跑、压力下会漏 case
- 「已经花了 X 小时删了可惜」→ 沉没成本，留着不可信的代码才是技术债

改 bug 同理：**先写一个复现 bug 的失败测试**，再按红-绿修。不写测试不修 bug。

## 3. 每个 Task 两阶段审查

每个 Task 实现完（已 commit），按顺序做两道审查，**顺序不能反**：

### 3.1 spec 审查（先做）— 验「做对了没、有没有多做」

不看实现者的自述，**亲自读实现的代码**，逐条对版本 / Task 要求核对：

- **漏做**：要求的功能都实现了吗？有没有声称实现其实没写的？
- **多做**：有没有做要求之外的东西？过度设计、塞「顺手加的」功能？
- **理解偏差**：是不是把需求理解歪了、解错了问题、对的功能用了错的方式？

结论二选一：`✅ spec 通过` / `❌ 发现问题：<逐条列，带 文件:行>`。有问题 → 回修 → **再审一遍**，直到 ✅。

### 3.2 code 质量审查（spec ✅ 后才做）— 验「建得好不好」

对这个 Task 的改动（`git diff BASE..HEAD`）审：

- 职责单一、单元能独立理解和测试、按计划的文件结构落地、本次改动没把文件撑得过大
- 错误处理、类型安全、DRY 不过度抽象、边界 case
- 测试测的是真实行为不是 mock、覆盖边界、全绿

### 3.3 审查分级与状态机

审查问题按严重度分级，决定何时修：

| 级别 | 处理 |
|------|------|
| **Critical**（bug / 安全 / 数据丢失 / 功能坏） | **立即修** |
| **Important**（架构问题 / 缺功能 / 错误处理差 / 测试缺口） | **进下一步前修** |
| **Minor**（代码风格 / 优化点 / 文档润色） | 记下，可later |

实现者报告状态机（控制循环用）：

| 状态 | 含义 → 怎么办 |
|------|------|
| `DONE` | 完成 → 进 spec 审查 |
| `DONE_WITH_CONCERNS` | 完成但有疑虑 → 先读疑虑，涉及正确性 / 范围的先处理再审 |
| `BLOCKED` | 卡住做不下去 → 补上下文 / 换更强模型 / 拆小 Task / 升级给用户，**别让它原样重试** |
| `NEEDS_CONTEXT` | 缺信息 → 补齐缺的上下文再继续 |

**两道审查全 ✅、Critical/Important 全修完，这个 Task 才算完成，进下一个 Task。**

> **自包含 + 可增强**：上面这套 spec / code 审查逻辑已内嵌，能独立跑。如果检测到项目里有 `/code-review` 命令或 `dwy-dev-qa` skill，Task 级或下面版本级的 code-review 可委托给它们做增强（更全面），没有就用内嵌逻辑。

## 4. 版本级 code-review（修到全绿才进下一版本）

一个版本**所有 Task 做完**后，对整个版本做一次完整 code-review：

```bash
BASE_SHA=<本版本第一个 commit 之前>
HEAD_SHA=$(git rev-parse HEAD)
git diff --stat $BASE_SHA..$HEAD_SHA
```

审查范围（对整版本 diff）：

- **计划对齐**：实现和实施计划 / 版本验收标准一致吗？偏差是合理改进还是问题？计划的功能都在吗？
- **代码质量**：职责分离、错误处理、类型安全、DRY 不过度抽象、边界 case
- **架构**：设计合理、性能可接受、安全、和周边代码集成干净
- **测试**：测真实行为、覆盖边界、全绿
- **production**：schema 变更有迁移、向后兼容、文档齐、无明显 bug

输出：Strengths / Issues（Critical / Important / Minor，每条带 文件:行 + 为什么 + 怎么修）/ Assessment。

**按级别修**：Critical + Important **全部修完**，每修一条跑相关测试确认无回归。Minor 记下。

> 项目有 `/code-review` 命令或 `dwy-dev-qa` skill → 委托它做版本级审查（增强）；没有就用上面内嵌逻辑。

**修完所有 Critical / Important（全绿）才进下一个版本。** 还有未修的 Critical/Important 就停在这一版。

## 5. 完成前验证（声称做完前，先拿证据）

```
没有刚跑出来的验证证据，不许声称「版本做完了」
```

声称这一版完成 / 进下一版 / 给交付报告**之前**，对照版本验收标准逐条验，**亲自跑命令看输出**：

| 要声称 | 必须有 | 不算数 |
|------|------|------|
| 测试通过 | 刚跑的测试命令输出：0 失败 | 「应该过了」「上次跑过」 |
| 构建通过 | 构建命令 exit 0 | 「lint 过了」「日志看着没问题」 |
| bug 修了 | 跑原始复现测试：通过 | 「改了代码，估计好了」 |
| 验收达标 | 逐条核对验收标准 checklist | 「测试过了就算完」 |

红旗——出现就停下先去验证：用了「应该 / 大概 / 似乎」、还没跑命令就说「搞定 / 完美 / 做完了」、准备 commit / 进下一版却没验证、信了 agent 的「成功」自述没自己核对。

**先跑命令 → 读完整输出 → 再下结论。** 不可逆操作（强推等）和声称完成，这条不许精简。

## 产物

- `plans/vN-<slug>.md` — 每个版本一份实施计划。
- 实际代码 + 测试 — **进项目源码**，频繁 commit。

## 交付报告（全部版本做完）

给用户交付报告：做了哪几个版本、各版本测试 / 构建结果（带证据）、code-review 全绿、代码落在哪、遗留的 Minor 项清单。

> 单版本内部修复用最小回归（仅相关测试）；改了共享工具 / 导出入口 / 基础设施，按影响面扩大到包级全量回归。

## 边界 / 禁止

- **禁止没有失败测试就写生产代码**——红-绿-重构铁律，违反就删掉重来。
- **禁止跳审查**——spec 和 code 两道都要，且 spec 在前 code 在后，顺序不能反。
- **禁止带未修的 Critical / Important 进下一个 Task 或下一个版本。**
- **禁止没跑验证就声称完成**——「应该过了」不算证据，必须有刚跑的命令输出。
- **禁止实施计划留占位符**（TODO / 待补充 / 类似 Task N）——每步给实际代码 + 确切命令。
- **禁止把代码写进 `docs/0to1/`**——只有实施计划进 `plans/`，代码进项目源码。
- **禁止在 main / master 上直接动手**（按项目分支规范走）。
