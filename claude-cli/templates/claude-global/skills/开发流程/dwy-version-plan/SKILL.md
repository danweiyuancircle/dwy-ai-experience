# dwy-version-plan · 版本规划

基于细 PRD 把产品切成若干可交付版本：v1 最小可用闭环 → v2 → v3…，每个版本是一个能独立交付的增量。

## 运行模式

上下文自适应，两种调用方式：

- **单独调用（默认）**：用户直接让你规划版本。从用户给的 PRD/功能清单或描述起步；产物落 `./version-plan.md` 或用户指定位置；**不读写 STATE.md、不依赖 `docs/0to1/`**。做完跑下方「门」即结束。
- **流水线调用**：`dwy-incubator` 调用，指令含「流水线模式」+ 前序产物路径（细 PRD）+ 落盘路径（如 `docs/0to1/06-version-plan.md`）。**STATE 记账（含选定版本、版本进度表）由 dwy-incubator 负责，本 skill 不碰 STATE.md**。

## 输入（切版本的依据）

- **细 PRD 是切版本的唯一依据**：每个版本包含哪些功能，必须能映射回 PRD 的具体页面 / 功能，不能凭空加。
- 看目标端和产品定位，版本节奏按端和定位定。
- 单独模式：用户没给细 PRD 就先问清有哪些功能/页面、核心价值是什么，再切。

## 怎么做（具体步骤）

套 `templates/version-plan.md`，按下面思路切：

1. **找 v1 最小闭环** — 从 PRD 里挑出「能跑通核心价值的最小一条路径」。用户能完整走完一次主流程、拿到核心价值，就是 v1。砍掉一切锦上添花。
   - ✅ 笔记 App v1 = 新建 / 编辑 / 列表 / 删除，一条闭环
   - ❌ v1 塞进多端同步、协作、AI 摘要、主题皮肤——这些进 v2+
2. **后续版本按价值增量切** — v2、v3 每个加一组**能独立交付**的功能。不要按技术层切（「v1 做后端、v2 做前端」是错的，那不是可交付增量）。
3. **大胆切大版本** — AI 写代码效率高，单版本可以比传统排期装更多。判据是「这一版能不能独立交付、独立验收」，不是「工时够不够一个 sprint」。能合并成一个能交付的闭环就别拆碎。
4. **写清依赖** — 哪个版本依赖前序版本的产物 / 数据结构。一般 v2 依赖 v1，但要显式写出来依赖的是什么（如「v2 的搜索依赖 v1 已落地的笔记表结构」）。
5. **每版写验收标准** — 这一版做完，怎么算「真的做完了」。要可验证：列出用户能完成的动作 + 可观测的结果，开发的完成前验证就照这个核对。

每个版本一节，写全：**目标（一句话）/ 包含功能（对应 PRD 哪些页面 / 功能）/ 依赖前序版本 / 验收标准**。

## 产物

落盘版本规划（单独默认 `./version-plan.md`；流水线按编排器给的路径）。套 `templates/version-plan.md`（含版本总览 + 每版本一节 + 一个填好的示例）。frontmatter：

```
---
status: done
updated: <date +%Y-%m-%d>
---
```

成稿要件：每个版本的「包含功能」都能映射回细 PRD 的具体页面 / 功能；v1 是最小可用闭环；依赖关系写清；每版有可验证的验收标准。落盘后核对：把版本里列的功能逐条回查细 PRD，确认没有 PRD 里没有的功能、也没把核心闭环拆散到多个版本，再声称完成（先验证再声称）。

## 门（过门确认）

用 `AskUserQuestion` 把版本建议摆给用户：
- 摆什么：各版本一句话目标 + 包含的主要功能 + 依赖关系（建议方案）。
- 问什么：「**这次做哪几个版本？（可多选）**」选项给 v1 / v2 / v3… 让用户勾选要一起做的版本，外加「调整切法」。

用户选定后，要改切法就改，直到确认。

## 边界 / 禁止

- **禁止脱离细 PRD 凭空加功能**——版本里每个功能都要能指回 PRD 某页 / 某功能。
- **禁止按技术层切版本**（后端版 / 前端版）——每个版本必须是能独立交付、独立验收的增量。
- **禁止把核心闭环拆碎**——v1 必须自己就能跑通核心价值，不能「v1 只有界面没逻辑」。
- **禁止漏依赖和验收标准**——每版都要写清依赖什么、怎么算做完。
