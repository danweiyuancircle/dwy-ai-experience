# dwy-tech-feasibility · 技术可行性

找 1-3 个成熟方案实现产品核心能力，**绝不手撸**。选对省半年，选错返工到死。同时判断要不要先写代码实测核心风险。

## 运行模式

上下文自适应，两种调用方式：

- **单独调用（默认）**：用户直接问某能力怎么实现 / 选什么技术。从用户描述的能力起步；产物落 `./tech-feasibility.md` 或用户指定位置；**不读写 STATE.md、不依赖 `docs/0to1/`**。做完跑下方「门」即结束。
- **流水线调用**：`dwy-incubator` 调用，指令含「流水线模式」+ 前序产物路径（市场分析）+ 落盘路径（如 `docs/0to1/02-tech-feasibility.md`）。按指令读前序、写指定路径；**STATE 记账由 dwy-incubator 负责，本 skill 不碰 STATE.md**。

## 输入（核心能力从哪来）

- 单独模式：从用户描述里拎出要实现的核心能力；不清楚就先问一句产品要做什么。
- 流水线模式：读编排器给的市场分析产物，拿到核心能力和差异化点。

技术调研只围绕**核心能力**转，别给还没定的边角功能选型。

## 怎么做

铁律：**先搜后造**，优先成熟开源方案，禁止手写已有主流方案的功能。

### 一、WebSearch 找方案（1-3 个）

1. 拆出产品的**核心技术能力**（如「实时语音转文字」「PDF 解析」「本地向量检索」），逐个搜主流实现。
2. 搜的标准（沿用 dwy「优先成熟开源方案」）：
   - npm / PyPI / GitHub **stars > 1k**
   - **近期有维护**（近半年有 commit / release）
   - 社区主流，不是冷门小众
3. 每个能力列 **1-3 个**候选方案，别只列一个（没对比说不清推荐）。

### 二、目标技术栈没有合适库 → 跨语言参考

目标语言/栈里搜不到合适方案，但**别的语言有成熟库** → 推荐那个库**供参考实现**，讲清两件事：
- 怎么参考：照它的核心算法/数据结构思路自己实现，还是直接调（子进程 / FFI / 服务化）。
- 怎么移植：关键逻辑在哪、移植难点是什么。

- ❌ 目标是 Python 但只有 Rust 有成熟库 → 直接说「没方案，自己写」
- ✅ 「核心算法 Rust 的 `xxx`（stars 8k）最成熟。两条路：① 用 PyO3 包成 Python 扩展直接调；② 照它的 `core/` 算法思路用 Python 重写，难点在 SIMD 那段。推荐 ①，省事且不丢性能。」

### 三、每个方案给四项 + 推荐

每个候选方案列：

| 项 | 说什么 |
|----|--------|
| 能力覆盖 | 核心能力它能做到几成，缺什么 |
| 成熟度 | stars / 维护活跃度 / 生产案例 |
| 适配度 | 跟产品技术栈、部署形态合不合 |
| 坑 | 已知限制、license、性能/体积代价 |

最后给 **推荐方案 + 理由**（敢下判断，别全列让用户猜）。

### 四、判断要不要写代码实测

| 判断 | 信号 | 建议 |
|------|------|------|
| **建议实测** | 有技术风险/不确定：新算法、硬件集成、性能未知、第三方 API 行为不明、跨语言移植没把握 | 接 dwy-spike 先写丢弃式 POC 验核心流程 |
| **跳过实测** | 技术成熟无悬念、方案有大量生产案例、就是常规 CRUD/调 API | 直接进开发，不必 spike |

把建议写进产物，给用户拍板。

## 产物

落盘技术可行性文档（单独默认 `./tech-feasibility.md`；流水线按编排器给的路径）。frontmatter：

```markdown
---
status: done          # 落盘且过门后才填 done；过门前 awaiting-approval
updated: <date +%Y-%m-%d>
---
```

正文必含：

| 块 | 内容 |
|----|------|
| 核心能力清单 | 产品要实现哪几项关键技术能力 |
| 方案对比表 | 每个能力 1-3 个候选，列 能力覆盖/成熟度/适配度/坑 |
| 跨语言参考 | 如有：推荐别的语言的库 + 怎么参考/移植 |
| 推荐方案 | 选哪个 + 理由（敢下判断） |
| 是否实测建议 | 建议实测（说清验什么风险）/ 跳过（说清为什么无悬念） |

## 门（过门确认）

落盘后先**自己核一遍**（先验证再声称）：每个核心能力都有候选吗、对比表四项填全了吗、推荐有理由吗、实测建议明确吗。

然后 `AskUserQuestion` 摆**方案对比 + 推荐**，问：

> 选哪个方案？要不要先写代码实测核心流程再往下走？

让用户同时定下「技术方案」和「是否实测」两件事。

## 边界 / 禁止

- **绝不手撸已有主流方案**——搜得到成熟库就用/参考，搜不到才自己写，且要在产物里写清「调研了哪些、为何都不用」。
- **每个核心能力至少给候选，不能空着说「自己实现」**——除非确认无任何开源方案。
- **推荐必须带理由，不和稀泥**——不「都可以，看你」。
- **目标栈无库时别直接放弃**——先看跨语言有没有成熟方案可参考/移植。
- 这步**只调研和选型，不写实现代码**。要验证可行性是 dwy-spike 干的事。
